The problem worth solving

Ask a language model for a travel itinerary and it hands back something beautiful, confident, and partly fictional — restaurants that closed years ago, coordinates in a parking lot two towns over, a "15-minute walk" that's really forty. For a trip planner that's a failure: someone is standing on a street corner trusting the output to be true.

So Wanderly never treats the model as a source of facts. The LLM decides structure — what kind of day this should be, how it's paced, why a place earns its slot. Every checkable claim it makes is then confirmed against an authoritative source, or removed before it reaches the screen.

The generation pipeline

Generative — the model decides
Deterministic — code verifies
01
Plan stops Model Skipped for single-city

A one-city trip needs no reasoning — the destination is the stop, so the LLM call is skipped entirely. Multi-city road trips call the model to choose a route and allocate nights per stop.

02
Build candidate pools Deterministic

Per stop, in parallel: geocode, pull real venues from Google Places across five buckets, and fetch hiking trails from a self-hosted OSM service. Results cache in Firestore for seven days, so a repeat trip to the same city costs nothing.

The pools are then re-ranked against the traveler's taste profile — personalization happens in retrieval, not in the prompt, which makes it inspectable.

03
Generate the itinerary Claude Sonnet

One structured tool-schema call produces the entire trip — every day, every activity, with times, descriptions, and categories. It selects from the real venues supplied above rather than recalling places from training data.

04
Validate, then repair surgically Validator Targeted repair

A deterministic validator checks the structural rules the model reliably gets wrong: meals inside real windows, at least seven activities per day, the day running to 8:30 PM, outdoor activities not scheduled after 3 PM, and at most one hike per day — it loves stacking three.

Failures don't trigger a full regeneration. The validator reports which days broke, and only those get a focused repair call — capped at two attempts and bounded by a 450s wall-clock budget. Past that the trip ships best-effort. A slightly imperfect itinerary beats a spinner that never resolves.

05
Ground against reality Deterministic

The anti-hallucination layer, run in a deliberate order. Every step is independently fault-tolerant — if an API is unreachable the pipeline keeps its best state and continues rather than failing the request.

  • ReconcileSnap each activity to its real Google Place — authoritative ID, coordinates, and map URL replace the model's guesses.
  • VerifyHard gate: anything that can't be matched to a real place or trail is dropped or replaced. A hallucinated venue cannot reach the user.
  • CohesionPull cross-city outliers back into the day's cluster, so one day never spans towns hours apart.
  • RouteReplace estimated travel times with real Google Routes data between the now-verified coordinates.
  • Drive legsFor road trips, attach real duration, distance, and an encoded polyline for the commute card.
06
Enrich images Deterministic

Photos resolve server-side before the "your trip is ready" notification fires, so the itinerary renders complete on open instead of popping in card by card.

Refining a trip by talking to it

After generation the traveler can restructure the trip in plain language — "it's raining today", "we're tired", "make this cheaper". The model doesn't rewrite the itinerary; it emits a minimal set of structured mutations (replace, remove, reorder), applied deterministically under two constraints: edits are clamped to the day being viewed, and pinned activities are excluded entirely.

Every edit re-runs the same grounding passes from stage 5, on Haiku rather than Sonnet — the task is small and structured, and the latency is felt directly by someone waiting on a tap.

Running it in production

Every generation spends real money at three vendors, which makes cost and abuse a design problem rather than an afterthought.

  • Firebase App Check on every endpoint — requests must originate from a genuine app binary, not a script hitting a public function URL.
  • Server-enforced credits — free tier gets 3 generations and 3 refinements a month. The client's opinion about remaining quota is advisory; the backend is authoritative.
  • Caching at every expensive layer — Places results in Firestore for 7 days; replacement suggestions in memory for 15 minutes with in-flight deduplication, so a preload and a user tap collapse into one call.
  • Hard quota caps on Places plus a GCP budget alert as a final backstop.
A bug worth keeping

The itinerary screen preloaded replacement suggestions for every activity on open, so "find alternatives" felt instant — but the suggestion endpoint charged a refinement credit per call. A free user could burn their entire monthly allowance by scrolling, before tapping anything. The fix separated reads from writes: browsing is free, the credit is charged on the confirmed change. When you charge is a product decision, not an implementation detail.

Testing what actually breaks

135 tests, aimed at the pure logic where a regression would be silent and expensive rather than at UI scaffolding that changes weekly.

  • Verification gate — unverifiable venues must not survive reconciliation.
  • Mutation scoping — a day-scoped edit must never touch another day.
  • Validation rules — meal windows, activity floors, the one-hike-per-day constraint.
  • Schedule reflow — re-timing a day must stay feasible against real travel times.
  • Directions precedence — place ID beats name beats coordinates, because coordinates were the original bug.

What I'd do differently

The pipeline got simpler, and it should have started that way. An earlier version ran seven stages, including a separate intent-extraction pass and k-means clustering. A single generation call over a well-built candidate pool replaced it — fewer moving parts, fewer failure modes, better output.

Grounding should be one composable pass, not five sequential ones. Each verification step re-walks the itinerary independently — readable, but wasteful, with ordering dependencies living in comments rather than types.

Generation latency is still the weak point. Multi-city trips can take minutes. Streaming days back as they finish would change how the wait feels far more than shaving seconds off the model call.
